# JITX checkpoint observability

`integrations/jitx/wandb_backfill.py` publishes a completed, immutable replay to the existing W&B project `philippe-fdesousa/copper-scar`. It never invokes native JITX, reruns an evaluator, or changes a candidate. Preparation needs Python's standard library only. Upload needs `wandb==0.30.0`, `requests`, `Pillow`, and `numpy`; the inspected Weave protocol is from `weave==0.53.9`.

Use a separate observability environment. Run the script with `--replay <completed-replay-directory> --ledger <stage1-ledger-directory> --output <new-local-bundle-directory>` to prepare locally. Add `--upload --key-file <private-existing-credential-file>` only when remote publication is authorized. The credential is read into process memory and is never included in the bundle, trace, command arguments, or source control. The script checks access to the named existing project and does not create alternative projects.

The completed replay has already selected the newest policy-v3 evaluation for each original physical action. The uploader verifies its saved board, evaluation, preview, and video hashes. It reconstructs the incumbent using lexicographic diagnostic cost and nonincreasing incorrect-connection, physical-error, and ERC-error guards. A historical `retain=false` on a later recheck does not erase that checkpoint's earlier incumbent status.

The loss is a vector of diagnostic counts, not a fabricated competition score. `loss/missing_pairs` is KiCad's missing-connection count. No attempted loss is logged for failed or unreliable records; their statuses, available board previews, and unreliable observed counts remain explicit. `incumbent/*` carries the best reliable incomplete board. `validity_gate=false` and the engineering limitations stay visible. Raw JITX and Copperhead costs are not directly comparable.

Shared fields include `track`, `comparison_kind`, `outer_index`, `attempt_id`, `policy`, `baseline_hash`, `loss/*`, `incumbent/*`, `native/invariants_ok`, `validity_gate`, `retained`, `board/attempted`, `board/incumbent`, and `routing/*`. `outer_index` means recorded action/checkpoint, including input and placed phases; it is not a claim of a completed optimizer generation. Missing scope or timing remains unknown. Trials 008/009 include saved net/terminal/layer/via selection and completion-limit audits. Neither provides a complete multilayer-routing proof.

W&B receives scalar curves, actual attempted and incumbent board images, the 5x replay, and an artifact with allowlisted checkpoint metadata and media. No broad directory, proprietary native source, authentication, console log, or unrelated file is uploaded. The Weave completed-call endpoint receives deterministic IDs, explicit historical-backfill labels, original evaluation timestamps, and the full W&B run path. These are checkpoint audit traces; no LLM calls or fresh PCB evaluations are invented.

Run IDs include a digest of the corrected comparison revision. Repeating the same bundle resumes the same run, skips existing checkpoint steps, and reuses deterministic trace IDs. A changed historical measurement creates a distinct revision/run so superseded metrics cannot contaminate an existing curve. Only one uploader should operate on a given output/run at a time. This is explicit backfill, not a background monitor; rerun after a newly completed replay to publish another frozen cutoff.

On completion the uploader reads back remote history and the final Weave output, downloads the final remote board image, and verifies its SHA against the locally prepared PNG. `upload-receipt.json` contains the run, charts, files, and trace URLs plus the exact cutoff and verification evidence. Upload errors leave the local bundle and all native checkpoints unchanged. Successful publication means observability is available, not that the PCB is valid.

API references: [W&B run resumption](https://docs.wandb.ai/models/runs/resuming), [Weave manual call tracking](https://docs.wandb.ai/weave/guides/tracking/create-call). The project's completed-call requirement was verified against its live API and installed Weave 0.53.9 transport/schema.
